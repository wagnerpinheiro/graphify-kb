# eval — tokens, time and quality: no KB × graphify only × KB + graphify

Purpose: show the user, with numbers tied to the data volume, how much the KB saves (or not) per question, what it costs to build, when it pays off, and whether cheaper answers are still correct.

## Configurations
| id | name | answering subagent may use | may NOT use |
|---|---|---|---|
| `baseline` | no KB, no graphify | Glob/Grep/Read over the converted `.md` files of the subset (the honest "Claude reads the files" approach; subagents may lack the Grep/Glob tools — allow read-only `grep` via Bash restricted to the subset files) | kb.py, kb/, graphify-out/ |
| `graphify` | graphify only | `graphify query/path/explain`, files inside graphify-out/ | raw/ directly, kb.py |
| `kb` | KB + graphify | the workspace `/kb` skill (`KB ask --source <each subset file>` first, query/show/page-text), graphify only for exploratory questions | Grep/Read over raw/; sources outside the subset |
| `kb-inline` (optional, recommended) | KB in the main context, no subagent | the main context answers with `KB` commands only (the way `/kb` is used day to day) | everything else; the answer key |

## Scope and authorization
- The baseline and the graphify build read whole documents → run only on a **subset the user authorizes per document** (AskUserQuestion with the candidate files and their size). Default subset: the 4–8 documents most queried, **≥ ~20k words** (smaller subsets are dominated by the fixed cost of each answering subagent, ~25–35k tokens, and show nothing about savings) and ≤ ~60k words.
- Everything runs in subagents. The main context sees only counts, scores and question texts — never answer keys or document excerpts.
- graphify for the eval is built over the same subset (`.graphifyignore`), in a subagent; its build tokens/time are the graphify build cost.

## Steps
1. `mkdir -p kb/evals/<YYYY-MM-DD>` (scratch work goes to the session scratchpad, e.g. `<scratch>/eval/`).
2. Volume: `KB volume --json > <scratch>/eval/volume_all.json`, then the subset (`KB volume "<path>" --json` per file, or filter the JSON) → `<scratch>/eval/volume_subset.json`.
3. Questions + answer key: one subagent reads the subset and writes `questions.md` (12 questions covering the types in `presets/<preset>/eval-questions.md` or the generic list below) and `answer_key.md` (expected facts, sources with page/sheet+row, scoring criteria 0/1/2, negative question verified absent). The main context reads only `questions.md`.
4. Answers: for each run r in 1..3 and each config c, launch **one subagent per question** (12 × 3 = 36 per run; per-question subagents are what make per-question tokens/time measurable). At most **20 subagents run at once**: launch in waves (e.g. 20, then one new subagent per completion notification). Prompt: the question, the config rules from the table above, "cite file + page or sheet + row", "say 'not found' instead of guessing", "report the number of tool calls", write the answer to `<scratch>/eval/answers/r<r>/<c>/<Q>.md`. For the `kb` config, point the subagent to the workspace `/kb` skill file (or, on a copy whose skill was not regenerated yet, to `~/.claude/skills/kb-setup/assets/templates/kb-skill/SKILL.md`) and give it the exact `--source` fragments of the subset.
   Cheaper option when the user prefers: one subagent per config per run answering all 12 (9 subagents); per-question cost then becomes an average.
5. As each subagent finishes, append its usage from the task notification (`total_tokens`, `duration_ms`, `tool_uses`) to `<scratch>/eval/runs.jsonl`:
   `{"run":1,"config":"kb","question":"Q3","type":"point-fact","tokens":31234,"duration_ms":41200,"tool_uses":3}`
   This data is only available in the notification — record it immediately.
   **Fixed cost of a subagent:** launch 3 trivial `general-purpose` subagents ("Reply only with 'ok', no tools") and record their usage in `<scratch>/eval/overhead.jsonl` (`{"tokens":20269,"duration_ms":5743}`). The report subtracts it to show the *context added* per configuration and to estimate the KB queried in the main context.
   **`kb-inline` (measured, no subagent):** the main context answers each question with `KB` commands only and writes `answers/r<r>/kb-inline/<Q>.md`; it must not read the answer key, and the question-writer subagent must not leak answers in its report (if it does, mark the affected answers "contaminated"). Log the exact commands per question in `inline/commands.json` (`[["ask", "..."], ...]`; a `{"args": [...], "chars": N}` entry when only a preview of a huge output reached the context). Then re-run them deterministically and count characters (command + output + answer), and convert with a measured chars/token ratio: 2 trivial subagents that `cat` a file of real KB outputs (tokens − fixed subagent cost ÷ chars; ≈ 1.6 for Portuguese KB tables). Append one `runs.jsonl` line per question with `"config": "kb-inline"`. This counts what enters the context, not the answerer's reasoning text.
6. Build costs: `<scratch>/eval/build_costs.jsonl` with one line per build activity measured (image-description subagents, extract-llm, graphify build, answer key), e.g. `{"kind":"graphify-build","config":"graphify","tokens":295961,"duration_ms":513093}`. For past builds use `KB costs --json` (logged with `KB log-cost` when the build happened); a known activity whose cost was not logged gets `"tokens": null` (the report then shows the build as "≥" and withholds break-even). Add `"scope": "subset"|"workspace"` to each line and log answer-key/grader costs with `"config": "eval"` (excluded from build cost). Build graphify over the converted `.md` of the subset so it sees the same text as the baseline.
7. Grading: one grader subagent reads answer_key + all answers and writes `<scratch>/eval/grades.json`: `[{"run":1,"config":"kb","question":"Q3","accuracy":2,"citation":2,"hallucination":false,"note":"..."}]`.
8. Report: `uv run ~/.claude/skills/kb-setup/scripts/eval_report.py --dir <scratch>/eval --out kb/evals/<date>/report.md` (also writes `summary.json`). Copy `questions.md` to `kb/evals/<date>/` (no answers, no excerpts).
9. Present: tokens/question (mean ± sd), time/question, tool calls, accuracy/citation/hallucinations per config and per question type; tokens per 1,000 words of the subset; projection to the whole workspace; build cost and break-even (number of questions after which the KB/graphify pays its build). Add improvement suggestions (e.g. a question type where `kb` is slow → saved query or topic/fact rule) to `kb/IMPROVEMENTS.md`.

## Generic question types (12)
lookup in a matrix/table · point fact · cross-document · figure/diagram content · document metadata · aggregation/count · relation between documents · negative (not in the sources) · exploratory/themes · conflicting values across documents · internal inconsistency within a document · deadline/date.

## Interpreting results (caveats to state in the report)
- Few runs and a grader from the same model family: indicative, not proof. With 3 runs, show the standard deviation; flag high-variance questions.
- Baseline cost grows with the corpus (it reads more text); KB/graphify per-question cost grows slowly — the projection uses words read per question (baseline) versus near-constant graph queries, stated as an assumption.
- Accuracy matters more than cost: never recommend a cheaper configuration that loses accuracy or citations.
- Savings vs. baseline are tested paired by question; a difference within ±2 standard errors is reported as "no significant difference", never as a break-even.
- Inside subagents, a baseline that greps (instead of reading whole files) can cost the same as the KB on a few documents — the fixed subagent cost (~20k tokens) dominates. The KB's practical saving is that its compact output may be read in the **main context**, while raw documents must go to a subagent: the report estimates this as "KB inline" (kb context added vs. a full baseline subagent). State that this saving comes from the rule, not from cheaper retrieval.
- Second real result (6 documents incl. 2 spreadsheets, 65.6k words, 1 run): baseline subagent 39.5k tokens/question, 24/24; KB subagent 42.2k, 22/24; **KB inline (measured) 4.2k, 22/24 accuracy, 20/24 citation → ≈ 9× fewer tokens than the baseline**. The inline answerer knew the engine well; a less skilled one makes more calls, so state a range (pessimistic bound: kb subagent *context added* ≈ 22k → ≈ 1.8×). KB losses came from spreadsheet auxiliary sheets not indexed (cover/legend, hidden sheets) — check them in `outline` during init.
- First real result (RFI workspace copy, 4 documents, 44k words, 1 run): baseline and KB both 24/24 accuracy and citation at ~36.6k tokens/question (no significant difference); graphify 15/24 and 13/24 (no page in `source_location` for most documents; misses table cells and figure content); KB inline ≈ 2.2× fewer tokens than a baseline subagent.
